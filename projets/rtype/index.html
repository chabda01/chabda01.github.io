R-Type

Notre version du shoot'em up des années 90, sur un moteur de jeu que nous écrivons nous-mêmes. Ici, vous jouez en solo, et vous voyez le moteur travailler : chaque entité, chaque composant, chaque règle.

Le projet d'origine est écrit en C++20, à quatre, et il est en cours. Cette page en est une version web : j'ai réécrit en JavaScript ma part, la logique de jeu, avec les mêmes règles et les mêmes fichiers de niveaux. Le réseau, le serveur et le client graphique sont faits par mes coéquipiers : ils ne sont pas dans cette démo.

Comment tester

  1. Lancez la partie. Cliquez sur « Jouer », bougez avec les flèches, tirez avec Espace. À droite, le tableau se remplit : chaque missile est une nouvelle ligne.
  2. Essayez le tir chargé. Tenez C une seconde, puis relâchez. Le gros missile traverse toute une file d'ennemis.
  3. Allez voir le boss. Choisissez « Niveau 3 · boss », puis « Bouclier » et « ×4 » pour y arriver vite. Seul son noyau orange prend des dégâts. Sa barre de vie change de couleur à chaque phase.
  4. Changez les règles. Passez en « hard », ou activez « Jeu à 70 % » et « Tir automatique ». Ce sont les options d'accessibilité du projet.
  5. Modifiez un niveau. Ouvrez « Modifier le niveau de départ », changez un count ou un type, puis « Jouer ce fichier ». Aucune ligne de code à toucher.

Au niveau 2, un Bydos laisse tomber la Force (le bonus « F »). Elle arrête les missiles ennemis. X la lance, X la rappelle.

Comment ça marche

Le moteur range tout le jeu dans un grand tableau. C'est l'architecture ECS : entité, composant, système.

  1. Une entité est une ligne. Juste un numéro. Quand elle meurt, son numéro est réutilisé.
  2. Un composant est une colonne. De simples données : une position, une vie, une arme. Il y en a 22 ici.
  3. Un système est une règle. Il passe sur chaque ligne qui a les colonnes dont il a besoin. Il demande « qu'as-tu ? », jamais « qui es-tu ? ».
  4. Un tick, c'est 14 systèmes dans l'ordre. Bouger, puis heurter, puis compter les morts. 60 fois par seconde, avec un pas de temps fixe.
  5. Le contenu est dans des fichiers. Les vagues sont en JSON. Un nouveau monstre peut s'écrire en Lua, sans recompiler.

Le boss est une machine à états. Sa phase suit la vie de son noyau : au-dessus de 66 %, un éventail de 3 missiles ; entre 33 % et 66 %, 5 missiles visés ; en dessous, un anneau de 10 missiles et 2 kamikazes toutes les 5 secondes.

Ce qui vient du projet, et ce qui change

Repris tel quel : le modèle ECS, les 14 systèmes et leur ordre, toutes les valeurs (vitesses, vies, cadences, phases du boss, bonus), les trois niveaux, le fichier de règles, les options de difficulté et d'accessibilité. J'ai comparé cette version au vrai programme C++, tick par tick, sur toute la campagne : mêmes entités, mêmes positions, même score.

Ce qui change : le navigateur ne sait pas lire le Lua. J'ai donc traduit à la main les deux scripts de monstres en JavaScript, ligne par ligne. Les bonus lâchés « au hasard » n'utilisent pas le même générateur de nombres que le C++.

Ajouté pour le web : les dessins (formes tracées par moi, pas les images du projet), le fond étoilé, les commandes tactiles, le panneau « sous le capot », et le mode test : choix du niveau, vitesse ×2 et ×4, bouclier, hitbox, niveau modifiable. Le jeu en ligne à 4, le mode versus et le son ne sont pas ici.

À quoi ça sert en entreprise

Simuler beaucoup d'objets

Une flotte de véhicules, des capteurs, des commandes en cours : des milliers d'objets qui changent d'état à chaque instant. Ranger les données en colonnes et les règles à part garde le code simple et rapide.

Laisser le métier régler le produit

Ici, un niveau est un fichier JSON et un monstre un petit script. Dans une entreprise, c'est une grille de prix ou une règle de calcul qu'on change sans redéployer le logiciel.

Un serveur qui décide de tout

La logique ne connaît ni l'écran ni le réseau. Elle peut tourner sur un serveur, dans un test automatique ou, comme ici, dans un navigateur. C'est le même principe qu'un moteur de règles métier.

Ce que ce projet montre

Du C++20 en équipe de quatre, une architecture pensée avant le code, environ 190 tests automatiques dans le dépôt, et une documentation pour que les autres puissent ajouter du contenu sans moi.
