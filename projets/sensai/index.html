SensAI

Un assistant IA qui tourne sur la machine de l'utilisateur, construit à quatre sur Ollama. Projet en cours. Ma part est la mémoire : ce que l'assistant garde d'un lancement à l'autre, et comment il fait de la place quand la conversation devient trop longue.

Le projet d'origine est écrit en Python et parle à un modèle local (qwen3:8b). Un navigateur ne peut pas faire tourner ce modèle. Cette page montre donc seulement ma partie, la mémoire : les mêmes règles, réécrites en JavaScript. Les réponses de l'assistant affichées ici sont des exemples écrits à la main, sauf une, qui est signalée. Aucune n'est générée dans cette page.

Comment tester

  1. Cliquez trois fois sur « Message suivant ». Chaque message reçoit une taille estimée et un score. La jauge se remplit. « merci » a un score de 0.
  2. Continuez jusqu'au septième message. La jauge passe le trait doré : les plus anciens messages sont remplacés par un résumé. Ouvrez l'onglet « Journal » pour voir ce qui a été écarté.
  3. Ouvrez « Base SQLite ». Tout y est encore, mot pour mot. Les deux lignes de l'horloge sont marquées volatile.
  4. Cliquez sur « Fermer et relancer ». L'historique revient du disque. Le tour de l'horloge n'est pas relu. Le résumé a disparu : il n'existait qu'en mémoire.
  5. Ajoutez une ligne au profil, puis relancez. Par exemple language et fr. Elle apparaît en tête de la liste envoyée au modèle. Écrivez ensuite vos propres messages.

Comment ça marche

Un modèle de langage n'a pas de mémoire. À chaque tour, on lui renvoie toute la conversation. Ma partie décide de ce que contient cette liste.

Se souvenir entre deux lancements

Après chaque tour, les deux messages sont écrits dans une petite base SQLite. Chaque conversation a son identifiant de session. Deux sessions ne se mélangent jamais. Au lancement suivant, le programme relit la session demandée avant le premier message.

La base garde aussi un profil : des paires clé et valeur, comme la langue ou le ton souhaité. Au lancement, il devient un message système placé en tête de liste.

Oublier ce qui n'est vrai qu'un instant

Un coéquipier a signalé un bug : on demandait l'heure, on relançait plus tard, et l'assistant redonnait l'ancienne heure. Il relisait sa vieille réponse comme un fait. J'ai ajouté une colonne volatile. Un tour qui passe par un outil ou une recherche web est marqué. Il reste dans la base pour le contrôle, mais il n'est plus relu au lancement.

Faire de la place

Le modèle a une taille de contexte limitée. Je compte les tokens à la louche : un token pour quatre caractères. Quand la liste atteint 90 % du budget, les anciens tours sont remplacés par un seul résumé. Les derniers tours (keep_last, 6 dans le projet) restent mot pour mot.

Dans le projet, c'est le modèle lui-même qui écrit ce résumé. Ici, il n'y a pas de modèle : la page met un texte d'exemple à la place et vous montre, dans le journal, la demande exacte que le projet aurait envoyée.

Avant le résumé, chaque ancien tour reçoit un score : 0 pour du remplissage (« ok », « merci »), 2 s'il contient un nombre ou un mot comme « décision » ou « problème », 1 sinon. Les tours à 0 sont écartés. Ce filtre a été ajouté par un coéquipier au-dessus de ma compression.

Ce qui est fait, ce qui ne l'est pas

Nous sommes quatre, chacun avec une partie. La mienne s'appelle « mémoire et persona ». La mémoire est écrite, testée et branchée dans le programme. Le persona, qui doit permettre de changer la personnalité de l'assistant en pleine conversation, n'est pas encore écrit. Ce qui existe aujourd'hui : des scénarios choisis au lancement, écrits par l'équipe. Ce sont eux que propose le menu « Scénario ».

Ce qui change par rapport au Python

  • Pas de modèle : les réponses et le résumé sont des textes d'exemple, toujours signalés. Une seule réponse est réelle, relevée dans le banc d'essai du dépôt.
  • Pas de fichier SQLite : deux tableaux avec les mêmes colonnes et les mêmes requêtes. Ils sont gardés dans votre navigateur, donc recharger la page revient à relancer le programme.
  • Le budget de la démo est de 500 tokens pour voir la compression vite. Celui du projet est de 4096.
  • Dans le projet, le profil se remplit par le code. Le petit formulaire est un ajout pour la page.
  • La recherche dans des documents, les outils et les garde-fous de mes coéquipiers ne sont pas repris.

J'ai comparé cette version au code Python sur des milliers de cas tirés au hasard, plus les cas des tests du dépôt : mêmes tailles, mêmes scores, mêmes listes, mêmes lignes en base.

À quoi ça sert en entreprise

Un assistant qui reprend un dossier

Un conseiller rouvre le dossier d'un client trois jours plus tard. L'assistant retrouve l'historique et les préférences sans qu'on lui répète tout.

De longues conversations sans casse

Un modèle local a un contexte court. Résumer les anciens tours permet de continuer sans planter et sans perdre les chiffres et les décisions.

Pas de réponse périmée

Un stock, un prix ou une heure lus par un outil ne sont vrais qu'un moment. Marqués volatils, ils sont redemandés au lieu d'être récités.

Ce que ce projet montre

Du Python testé, une base SQLite avec migration, un bug trouvé en équipe puis corrigé, et un travail à quatre sur le même dépôt.
